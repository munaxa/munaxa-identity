# Architecture

## Why this repository exists

Munaxa Work's ADR-0001 says authentication belongs to Platform. That sentence had no referent:
Platform ships authentication _libraries_ and no authentication _service_, and its own principles
forbid it ever shipping one — "no database driver, no Redis client, no email vendor, no cloud SDK
appears in any package", and "the platform never migrates a schema, never owns a table". An
authentication service is durable state before it is anything else.

So the issuer had to be a product. Not Munaxa Work, which would have given one business system
custody of ecosystem-wide credentials and contradicted its own ADR-0001. Not a shared package,
because `PLATFORM_ENGINEERING_STANDARDS.md` §4 rule 3 — "Products MUST NEVER import another
product" — is absolute. A sixth peer product, admitted by
[ADR-0001 in the corporate repository](https://github.com/munaxa/munaxa/blob/main/docs/adr/0001-munaxa-identity-is-a-sixth-peer-product.md).

## Ownership

|                            | Owns                                                                                                                   | Never touches                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Platform** (`@munaxa/*`) | Password hashing, signing, token format, session lifecycle, RBAC resolution, rate limiting, CSRF, audit chaining       | Any table, any driver, any product vocabulary                      |
| **Identity** (here)        | Accounts, credentials, sessions, refresh lineages, roles, assignments, its own audit trail, the authentication service | Work's tenants, Work's business data, Work's permission vocabulary |
| **Work**                   | `workforce_user`, `tenant_membership`, business data, the Work permission catalogue, tenant isolation                  | Any credential, any session, any signing key                       |

Neither product appears in the other's `package.json`. What crosses is a signed token, a public
key, and a generated JSON file.

## The flow

```
Browser ──POST /api/auth/login──► Identity            the only place a plaintext password exists
                                    │
                            LoginService              scrypt, timing-safe, dummy hash on a miss,
                                    │                 lockout checked before verification
                            SessionManager            idle and absolute deadlines, concurrency limit
                                    │
                        PermissionResolver            role graph → effective grants
                                    │
                    TokenService.issueAccessToken({ …, permissions })   ← the line that matters
                                    │
        Set-Cookie: __Host-mx_session  (httpOnly, Secure, SameSite=Lax, Path=/, no Domain)
                                    │
Browser ──GET /──────────────────► Work portal        reads the cookie server-side, never in script
                                    │
                    Authorization: Bearer …           forwarded server-to-server
                                    │
                              Work API                verifies with the configured public key
                                    │
                     app_memberships_of(sub)          which Work tenants this person may act in
                                    │
                   PlatformPermissionChecker          `perms` mapped against a closed catalogue
                                    │
                          PostgreSQL RLS              tenant isolation, forced, no BYPASSRLS
```

`permissions: resolved.permissions` is passed on **both** the login and the refresh path. Platform
emits the `perms` claim only when the caller supplies it, and Platform's own reference login example
does not — a service written by copying it authenticates perfectly and authorizes nothing. Resolving
only at sign-in would be the subtler version of the same bug: permissions frozen for the thirty-day
life of a refresh lineage.

## Tenancy

Two tenant concepts, deliberately not the same identifier.

```
Identity organisation  <IDENTITY_TENANT_ID>   ↔   Work tenant  <generated by Work's db:bootstrap>
```

An **organisation** is one customer of Munaxa and the scope of every role assignment, because
Platform's roles are tenant-scoped. A **Work tenant** is answered by Work's `tenant_membership`, and
Work ignores the `tid` claim entirely (its ADR-0032/0033). The relationship is an operational
mapping recorded in the runbook; no code asserts the identifiers are equal.

One token carries one organisation's permission context — `PermissionResolver.resolve` and
`issueAccessToken` are both single-tenant, which is a Platform property rather than a choice. So the
session spans organisations and the access token does not: `/auth/refresh` takes an optional target
organisation and re-issues.

## Second factor, recovery and sessions

- **MFA** (ADR-0005): TOTP from Platform's `MfaService`, secrets sealed under a dedicated key ring
  and bound to their account, recovery codes stored as keyed hashes. A right password for an
  account that needs a factor yields an opaque single-use challenge (`__Host-mx_mfa`, in Redis),
  never a session; `MFA_POLICY` decides who needs one. Changing or removing a factor, regenerating
  recovery codes and changing the password need a recent reauthentication with the factor.
- **Password recovery** (`docs/runbooks/password-recovery.md`): one-time links, completed in one
  transaction that also ends every session. It never changes or removes a factor, and it never
  signs the person in. Disabled in production until a production email transport exists.
- **Sessions** (`docs/runbooks/revocation.md`): people list and revoke their own sessions;
  revocation is one-way and refresh re-checks it.
- **Operator commands** (ADR-0006): lost-device reset, account disable, ending pre-enforcement
  sessions and MFA key re-encryption run as one-off tasks of the service through the same code,
  row-level security and audit chain. There is no administration API.

## What is deliberately absent

**No `SECURITY DEFINER` function, and no resolver role.** Munaxa Work needs both, because it must
answer "which tenants may this person act in?" before any tenant is in context, over rows that are
personal data (its ADR-0077). Identity never has that problem: every Platform port method takes a
tenant as its first argument, and a sign-in resolves its organisation from `identity_tenant` — a
table with no personal data — before touching an account. Adding that machinery here by analogy
would open a hole for a problem this schema does not have. The RLS suite asserts the absence.

**No foreign key from sessions, refresh tokens or reset tokens to the account.** The Platform ports
treat the user id as opaque and never promise an account row exists; the conformance suite stores
records for users it never created. An adapter that refuses them does not satisfy the port.

**No self-registration endpoint.** Accounts are provisioned administratively, as in every Munaxa
product.

## Identifiers

Platform's `TenantId`, `UserId` and `SessionId` are branded _strings_, not UUIDs — `ROOT_TENANT_ID`
is literally `'root'`, and `SessionManager` mints `sess_…`. Columns holding them are `text`.
Identity mints UUIDs for what it creates; the columns do not require one, because a column that
rejects what the platform produces fails on the platform's own vocabulary. This was found by a
crash, not by reading: an edge audit event carried `ROOT_TENANT_ID` into a `uuid` column.

## Database

Two roles, as in every Munaxa product: a privileged owner for migrations, and `identity_app` —
non-superuser, `NOBYPASSRLS` — at runtime. Every tenant-bearing table carries
`force row level security` with a policy reading a transaction-local setting, so a query with no
tenant context matches nothing rather than everything. `identity_audit_event` is append-only by
_grant_: the runtime role holds `select` and `insert` and nothing else, so it is a privilege the
application cannot talk its way out of rather than a rule it is trusted to follow.

`identity_tenant` is the one table without RLS, and the reason is in the schema: it is what a tenant
context is resolved _from_, it holds no personal data, and it is not writable at runtime.

## Cache

Redis, and the configuration refuses an empty `REDIS_URL` in production. Three things run on it and
each degrades differently without it: login lockout stops being a limit, the permission cache stops
being coherent across replicas, and the rate limiter becomes advisory.

The client is `ioredis`, not `node-redis`, and that is a correctness requirement rather than a
preference — see `docs/adr/0002-ioredis.md`.
